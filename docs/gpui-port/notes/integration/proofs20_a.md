## Rows that are not test-only after all

- `ipc:debug_attachable_processes`: Attach to Process only fills `Debugger::overlays.attach`; nothing in `app-gpui/src/workbench/` or the debugger views draws an Attach popup (no reader of `overlays.attach` outside `debugger/actions.rs`), and `action:debug.attachToProcess` is unticked. Missing: the popup view (filter, groups by `kind_label`, Enter attaches) and its layer in the window. The op itself lists the machine's real processes through `ps`, so a test should then assert a child process the test starts.
- `ipc:debug_send_input`: `DebugState::send_program_input` has no caller outside its unit test; the debug console has no input that types into a `runInTerminal` program (the webview's console does, through `readsProgramInput` / `sendProgramInput`). Missing: the console input while `reads_program_input()` holds, emitting `DebugSendInput`.
- `ipc:java_build_workspace`, `ipc:java_debug_server`: in a test build the driver answers both from `JavaBuildAnswer` / `JavaDebugServerPort` before reaching `java::java_build_workspace` / `java::java_debug_server`, and the real ops need jdtls (`LspManager::jdtls` finds the `java` server named `jdtls`). The existing hot swap tests therefore do not prove these rows. Missing: a fake language server registered as the `java` language's `jdtls` in the temp config folder answering `vscode.java.startDebugSession` and `java/buildWorkspace` (and what `java_configure_compiler` asks), with the two seams absent in that test.
- `ipc:db_connect`: the window never issues `DbOp::Connect`: expanding a source goes straight to `DbOp::Schemas`, `DatabaseStore::connect` has no caller in the window, and `plugin_connect` serves `db.pluginConnect`, which is not registered natively. The webview calls `db_connect` on every source/database expand (`DatabaseView.tsx` `load`) and in `db.pluginConnect`. Missing: `db.pluginConnect` (and, for parity, connect-before-load on expand).
- `ipc:db_databases`: only `lists_databases` sources (Postgres without single-database) load databases; SQLite and ClickHouse never do. Needs a Postgres server.
- `ipc:db_schema_objects`: called inside `DbOp::Tables`, but SQLite and ClickHouse have no routines or sequences (`sql::routines` / `sql::sequences` are `None`), and its error is dropped with `.ok()`: nothing a test can see tells it was called. Needs Postgres, MySQL, SQL Server or Oracle.
- `ipc:db_set_ssh_secret`, `ipc:db_trust_ssh_host`: the remedies come only from `ide-ssh` errors ("SSH password required", "Unknown SSH host key"); they need an SSH server, and Trust writes `~/.ssh/known_hosts`.
- `context:run.updatableRunning`: ON needs a running `spring-boot` or `tomcat` configuration (`is_updatable`); spring-boot goes through `resolve_application` (jdtls `ResolveLaunch`) and Tomcat needs a Tomcat install. The triage's "CMake build" is the `run.cmakeBuild` key, not this one. Also a difference: `RunContext::of` passes `&[]` for debug sessions while the webview's `updatableSessions()` counts debug sessions of updatable configurations too.

## Tests most likely to fail first

1. `proofs20_database`: a new fixture (loopback fake ClickHouse HTTP server, one request per connection, `Connection: close`). If reqwest pipelines or retries differently, or a system HTTP proxy applies to `127.0.0.1`, requests never reach it; the wait for `analytics` then runs out, and the tree's error row under `warehouse` tells why. The owner may veto the fixture: without it the row stays undone (SQLite never asks for a password).
2. `proofs20_run::debug_context_debugs_a_python_file_...`: depends on `prepare_debugpy` probing the language's own command (the launcher answers `-c` with exit 0) and on the fake adapter reading `program` from the debugpy launch (`debugpy_launch` sets it from the script argument). `ipc:sdk_python_effective` no longer depends on it.
3. `proofs20_build_title`: uses the private `build_project`, `maven_project`, `close` and `MAVEN_KEY` of `workbench/build_tools.rs` tests, a file the integrator is editing; and Build Project must reach the stand-in Maven through `check_build` / `build_run` (the `ran` mark). Also fragile: the exact More Actions labels in `proofs20_run_widget` (a shortcut or disabled marker in a row label breaks the comparison).
