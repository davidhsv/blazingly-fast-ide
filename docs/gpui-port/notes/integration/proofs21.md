## Not test-only after all

- **linkage › "drops a late link result after the user changes projects".** The native code drops an answer that arrives after the project changed (`gradle_linked` checks `epoch`). No test can drive that interleaving: nothing can hold `gradle_link_projects` while its call is pending (no test guard like `guard::check_sync`, and no stand-in process). The interleaving that can be driven is a project change while the picker is open. There the native code does NOT do what the webview does. `store.ts:337` returns when the project changed during the pick. `link_gradle_projects` goes on and calls `gradle_link_projects(host, "w1", …)`, which now resolves to the new project. `set_gradle_projects` then writes the first project's build into the new project's `languages.java.gradle.linkedProjects`. External paths are accepted (`normalize_linked_projects`); I read this in the source and did not run it. The model is then dropped by `epoch`, but the setting stays. What is missing: the epoch check after the picker (hunk above). The late-answer case would also need a hold in the test build to be provable.
- **`ipc:user_font_data`.** `theme::installed_fonts::system_font_names` panics in test builds by design, and the test may not read or install anything under the user's home. What can be asserted is only what `settings_view::custom_controls::tests::the_editor_draws_with_the_font_applied_on_the_font_page` already asserts on an injected list. Not enough. The check needed is a real window: apply a family that exists only in `~/Library/Fonts` on the Font page, then see that the picker lists it and that the editor's `text_style` family is it. That CoreText's all-families list includes user-domain fonts comes from reading the source, not from a measurement.
- **`ipc:window_start_drag`, as a test.** In gpui-pre-macos, `on_hit_test_window_control` is a no-op (`window.rs:2083`). The test window stores the callback but never calls it, so the title bar's `.window_control_area(Drag)` can neither be observed nor have any effect on macOS. On macOS the drag and the double-click zoom are AppKit's: `window_options()` keeps `app_owns_titlebar_drag: false`, so `opaqueRectForWindowMoveWhenInTitlebar` returns an empty rect. Hypothesis, not measured: AppKit drags only within its own title bar strip, so the lower part of the 40 px bar (`h-titlebar`) may not move the window. To check it, drag the bar 4 px above its bottom edge in the real app and see whether the window moves.

## Differences from the webview seen while reading (not tested)

- `TitleBarFrame::native()` is `frameless: false` on every OS. The webview's title bar is frameless with a main-menu button on Windows and Linux (`platformInfo.ts`). `chrome.rs` says this is deliberate (the window keeps the OS frame). The title-bar test asserts the native rule.
- Execute Maven Goal: the spec's literal `site-deploy ` holds only for a model with no plugins. With a real POM the lifecycle plugins add goals after the phases. The wrap test therefore takes "the last completion" from the drawn rows, and the `.tsx` does the same with plugins.
- Enter on `-Dunknown` runs the line in a window with a Maven project, in both apps. It is inert in the spec only because the spec's model is null.

## Most likely to fail first

1. `a_build_picked_after_the_window_changed_projects_is_linked_nowhere`: fails by design until the fix hunk. If the stale link and the second link race (read-modify-write of the same setting), it can also pass spuriously on the unfixed app. It cannot fail spuriously once the fix is in.
2. `clears_selection_when_typing_changes_the_rows_and_ignores_section_clicks` and `resets_selection_when_changing_the_gradle_build_used_for_completion`: Tab after a mouse press inside the popup. If the press moves focus off the text field (a parent's `track_focus`), Tab no longer reaches the field's key claim. That would be a real native bug: the field should keep focus, so mark the section and chip presses handled or refocus in the handler, not in the test. Also: the list's scroll offset may not clamp back to 0 after the rows shrink (the wait would then time out); the heading's position is derived (28 px row) because sections carry no `debug_selector`; and the emptied-model wait depends on `load_build` returning `None` for every linked build once their scripts are gone.
3. `registers_the_maven_tool_window_only_while_the_project_has_a_pom`: unregistering a tool window while it shows (the panel is removed in `sync_build_tool_windows`), and `stripe:maven` being drawn at the default test window size. The right-half assertion assumes that the right stripe is drawn at the window's right edge.

Also worth watching: `routes_reload_to_the_chosen_independent_build` depends on the linked build's `dir` (`libs/other`) equalling `p.root.join(dir) == root.join(&g.dir)` in `build_sync`'s filter, and on the stand-in reporting `:app` under `libs/other/app` (the fixture creates that folder).
