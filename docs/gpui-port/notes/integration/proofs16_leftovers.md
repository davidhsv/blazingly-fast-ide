## Tests most likely to fail on the first run

- `a_running_plugins_permission_request_shows_the_permission_page_and_ok_grants_it`: it assumes the app's plugins folder is `<home>/data/plugins` (inferred from `plugins_window.rs:1191` and `plugins.rs`'s `home.path().join("data/plugins")`) and that `Plugins::init` loads the folder. It also assumes a plugin command run through `run_action` carries the window's label as the client, because the `ConsentRequested` event is dropped for another client (`plugins_window.rs:382`).
- `selects_and_clears_a_plugin_theme`, `turning_a_plugin_off_…`, `projects_command_contributions_…`: they hand the app's own host to `Workbench::use_plugin_host` (`plugins_window.rs:185`), which no existing test does. Reading the code, that is the same host the window would use anyway. If it misbehaves, use `trusted_project` + `plugins.settings` + `settings_plugins_page()` instead.
- `selects_and_clears_a_plugin_theme`: the Themes section's buttons must be drawn inside the Welcome screen (they are clicked by debug selector), and the page must learn the stored theme through `set_appearance` for Use Default Theme to show.
- `executes_host_command_requests_…_not_found`: `plugins.settings` receives the argument `"argument"` that api14 passes. If its handler rejects an argument, the answer is an error.
- `a_plugins_editor_tab_entry_…`: it assumes `editorTab.context` needs plugin API 1.4 at most. It also assumes that after the menu closes the editor has the keyboard again, because Insert Date fails without a focused editor.
- `keeps_a_plugin_log_tab_…`: with two tabs, `editor.nextTab` must cycle back to the log tab.
- `the_gutters_menu_without_a_project_…`: a lone file must have a gutter at the same place as in a project, and `bookmarks()` must be readable without a project.
- `adopts_the_first_icon_theme_…`: the disabled plugin's checkbox must be clickable (`enabled: Some((false, true))`).
