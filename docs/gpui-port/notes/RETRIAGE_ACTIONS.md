How a row was classified (script `classify.py`, output `classify.json`): the registration is the innermost bracket around the id's string literal (an `id:` object, a helper call or a table entry), plus, one level down, every definition that registration names in the same file or imports from a relative or `@/` module, plus the upper-case constants those definitions name (the `when` clauses: TEXT_WHEN, EDITOR_WHEN). `same`: all of it equal after whitespace at the same line; `moved`: equal at another line. Any change in that text, in the id's bindings in the six keymap files, or in the lines elsewhere in `src/` that name the id (menus, toolbars, callers) makes a row `changed`. Rule for references: a new or changed menu, toolbar or button placement lowers the row unless native has the same placement; a new caller in code keeps it. References are compared as a multiset of whitespace-free lines, so a second identical menu entry counts. Template-built ids (`project.option.${key}`, the bookmark mnemonics, `toolwindow.${id}`) were compared by hand; they are `moved`. A sweep of every row registered through a helper or a table (`step`, `occurrence`, `schemeSwitch`, `appearanceToggle`, `copyPath`, `editorAction`, `mode`, `edit`, the `find.popup.*` table) compared the helper's callees one level further (`deep.py`); only `copyPaths` changed (the clipboard call).
