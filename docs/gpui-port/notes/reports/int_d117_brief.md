## Part 0c (small, under `crates/`: this brief names the seam; rule 3 of `$S/int_rules.md` applies in full): tests read no version-manager configuration of the user

Since the build model loads on every project open, a project that names no JDK reaches `ide_sdk::apply::project_jdk` → `ide_sdk::pinned::pinned_install`, whose `global_configs()` (`crates/ide-sdk/src/pinned.rs`) reads the user's `~/.config/mise/config.toml` (or the file `MISE_GLOBAL_CONFIG_FILE` / `MISE_CONFIG_DIR` / `XDG_CONFIG_HOME` name). It is a read, and the same lookup serves Node, Go, Maven and Gradle (`crates/ide-sdk/src/apply.rs`), so tests have probably read that file for a long time; tests must read nothing under the user's home. Add one process-wide switch on the pattern of the two that exist (`ide_build::maven::set_maven_user_home`, `ide_sdk::java::set_jdk_candidates`): `ide_sdk::pinned::set_global_configs(Option<Vec<PathBuf>>)`, `None` (the default) keeping today's behaviour exactly, read by `global_configs()`; make `ide_host::ops::build::isolate_from_user_home` set it to an empty list as well (keep that function's signature), so the native test build, which already calls it in `app-gpui/src/backend.rs`, is covered. Check whether `pinned.rs` reads any other file outside the project for asdf or other managers (`~/.tool-versions`, `~/.asdfrc`, `ASDF_*`) and put those behind the same switch. One test binary of its own (`crates/ide-sdk/tests/pinned_global_configs.rs`): with a config written in a temp folder and named through the environment variable the code already honours, the pinned version is found; after the switch is set to an empty list it is not; after `None` it is found again. No existing signature changes, no IPC type changes, nothing under `src/` or `src-tauri/`.

Then from the WORKTREE ROOT, one heavy build at a time: `cargo test -p ide-sdk`, `cargo test -p ide-host`, `cargo clippy -p ide-sdk -p ide-host --all-targets -- -D warnings`, `cargo test -p openidea export_bindings`, and `git status --short src/ src-tauri/ e2e/ package.json` must print nothing. Put each result line in the report. Then prove it from the native side with a test in `app-gpui`: a project with no JDK setting opens, its build model loads, and a global config file a test wrote under a temp `XDG_CONFIG_HOME`-style folder cannot be what the lookup used (assert through what the app shows; do not set process environment variables in a test: no new `unsafe`). If that cannot be asserted from the window, say so and rely on the crate test.

## Part 0d (small, tests only unless the app is wrong): the build tools' conditions read on and off

The Maven and Gradle actions are registered with the conditions `projectOpen && build.maven` and `projectOpen && build.gradle` (context keys set in `app-gpui/src/workbench/build_tools.rs`), and the tool windows with `build.maven` and `build.gradleWindow`. No test reads them off. Add tests in `workbench::build_tools::tests` (use the module's own fixtures: a stand-in Maven home and JDK named in the project's settings, a stand-in `gradlew` in the temp project; the test build refuses anything else): in a trusted project with no `pom.xml` and no Gradle build, `build.maven` and `build.gradle` are off, every `maven.*` and `gradle.*` action the window registers is unavailable through the registry (as the existing tests read an action's availability; `run_action` on an unavailable action must do nothing), and the Maven and Gradle tool windows are not offered; after a `pom.xml` is written and the model is read again the Maven half turns on while the Gradle half stays off; the same for a Gradle build. Compare with the webview's rules first (`src/features/build-tools/index.ts`: `MAVEN_WHEN`, `GRADLE_WHEN` and when each context key is set) and fix the app if it differs. Also read `gradle.linkProjects` off (its condition is `projectOpen && !workspaceOpen`: unavailable with no project open, on the Welcome window). Rows this earns: `context:build.maven`, `context:build.gradle`, and the `action:maven.*` / `action:gradle.*` rows that are recorded partial only for this.
