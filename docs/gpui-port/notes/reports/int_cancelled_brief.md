## Part A: Show Usages ran, its search came back `Cancelled`, and nothing was shown

For days single tests that wait on something an action should bring have failed once in many whole-suite runs and passed alone (six failures in five tests; `docs/gpui-port/DECISIONS.md` D126 to D130 list them, and two earlier hypotheses were wrong). The waits print a report since D130. This is the first failure with that report, in my whole-suite run of 2026-11-16 (log kept: `$S/verify_dsetc_suite2_FAILED_show_usages.log`; grep it for `---- workbench::popup_placement::tests::show_usages_with_the_caret_on_no_name` and read the whole block, both "state when it ran out" and "state now").

Test: `workbench::popup_placement::tests::show_usages_with_the_caret_on_no_name_opens_no_popup_and_says_so` (`app-gpui/src/workbench/popup_placement.rs:354`). It opens `src/alpha.rs`, puts the caret at 1:0 (no word there), runs `find.showUsages` and waits for the hint "No usages found. Based on syntax (language server not ready)". What the report measured:

- `active editor: …/src/alpha.rs version=0 caret=1:0 … word at the caret=None hint=None`, `tabs opening: []`: the editor was ready and had the keyboard.
- `show usages: request=Some(RequestId(242)) flow=UsagesPopupFlow { … target: Some(Target { caret: … word: None … }), search: None, tickets: 0, light_mode: true }`.
- The trace, in milliseconds: `…883 show usages at Some(UsageCaret { … word: None … }): [Fetch(SyncIndexes { path: … })]`, `…883 action find.showUsages ran: ok`, `…896 usages popup: search cancelled: IdeError { kind: Cancelled, message: "cancelled", data: None }`. Then nothing for thirty seconds.

So, measured: thirteen milliseconds after the action ran, a fetch of the usages search was answered with an error of kind `Cancelled`, and `UsagesPopupFlow::apply` (`app-gpui/src/code_insight/usage_search.rs`, the `FetchStep::Failed` arm: `if is_cancelled(&error) { … return Vec::new(); }`) drops a cancelled search without a word, which is right when the user or a newer search cancelled it and wrong here: nobody did. Not measured: who cancelled it. Find that out; do not guess. Leads, each to confirm or refute by reading and then by a test that forces it:

1. `Host::begin_project_request` (`crates/ide-host/src/lib.rs`) hands out a token that is cancelled at once when the window's project is not trusted at that instant (`if self.project(window).is_ok_and(|p| !p.is_trusted()) { token.cancel(); }`). Which fetch of the usages search goes through it (read `app-gpui/src/workbench/code_insight.rs` around the `FetchRequest` match and the backend functions it calls, and the Tauri adapters for the same calls), and can the test's project be untrusted for an instant after `search_project` returns (read how the fixture trusts the project and whether trust is applied after the project opens: an ordering between opening and the trust decision)? If that is it: what does the webview show when a search is refused for trust (a Restricted Mode notice? nothing?), and the native app must do the same instead of going silent; and the fixture must not hand a project to a test before its trust has settled.
2. `Host::cancel_request(id)` cancels an id "also when it has not begun yet (it then starts out cancelled)". The flow holds `request=Some(RequestId(242))`: read where the usages popup allocates a request id and where it cancels the previous one (`cancel_request` callers in `app-gpui/src/workbench/code_insight.rs` and `code_insight/`), and whether a cancel meant for an older search can name the id of the new one (the id taken before the cancel is sent; the same id reused for two fetches of one search; a cancel sent from `Drop` of an older flow that shares the id). Also `Host::end_request` and `project_requests`: closing another project window of the same test process cancels the requests of its window label: do two tests share the label `w1` in one process, so that one test's `close_project` cancels another test's request (the tests of a whole-suite run are threads of one process with one global `Backend`? read how `start(cx)` builds the backend: per test or shared)? This lead would explain why the failures happen only in whole-suite runs.
3. The backend's own cancellation: an index sync or a text search superseded by another one of the same window (read the search ops the usages flow calls for a "newer request cancels the older" rule), started here by the editor opening the file.
