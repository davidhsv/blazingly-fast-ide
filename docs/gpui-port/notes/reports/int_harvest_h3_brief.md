## For each row

1. Read the row's text below, then the webview's source and spec for it at HEAD (the row's source is in `docs/gpui-port/INVENTORY.md`; grep the row's id), and write down exactly what the user sees or what lands on disk for each case its "Missing:" clause names.
2. Write the test in the existing test module that already has the harness for that area (copy the setup of a neighbouring test; name the test after the behaviour, in the module's style). It starts from the action through the registry, a key, a click or a backend event, on the real backend in a temp home and project where the area's tests do so, and asserts what the user sees or what is on disk. A test of a model alone does not count.
3. Run it. If it passes: prove it can fail with one mutation of the native code it exercises (a script run that restores the file in a trap and compares hashes; `docs/gpui-port/notes/tools/mutation_check_example.sh`). If it fails: the behaviour the row claims is not there or differs from the webview. When the fix is small (about forty lines, no new view, no new backend call), make it and say so; otherwise remove your test for that case, leave the row, and report what is missing with the webview's `file:line` (that is a correction of the row, and as useful as a raised one).
4. Never weaken an assertion of an existing test. No `#[ignore]`, no stubs, no new dependency, no `unsafe`.

Order: the rows in the order listed. When about two thirds of your budget is used, finish the row in hand, run the gates on what has landed and report which rows are done and which are not started. Never leave a row half done.
