## 2. The engine's behaviour as a checklist

IDs are stable. A slice in section 5 names the IDs it delivers. "Pos" means (line, UTF-16 column), as the engine works (`core:indexFromPos` via `cm6:9-26`). Unless an item says otherwise, a key is matched in the contexts normal, visual and operator-pending.

### 2.1 Modes and mode changes (MD)

- MD-01 Normal is the initial mode. `enterVimMode` signals `{mode:"normal"}` (`core:320-329`). [W]
- MD-02 Insert is entered by `i a I A gi gI o O s S c C` and friends, with `{mode:"insert"}` (`core:3050-3127`). [W]
- MD-03 Replace is entered by `R`, with `{mode:"replace"}`. `<Ins>` in Insert toggles Insert↔Replace (`core:3039-3049`). [–][E]
- MD-04 Visual char, line and block, with `subMode` `""`, `"linewise"` or `"blockwise"` (`core:3128-3161`). [W]
- MD-05 `<Esc>` leaves Visual, then Insert. With neither active it does nothing but clear pending input (`core:933-946`). Leaving Insert moves the caret one left unless `keepCursor` (`core:6702-6704`). [W]
- MD-06 `<C-[>`, `<C-c>` and `<C-Esc>` mean `<Esc>` in all modes (`core:93-98`). In the adapter, `<C-c>` with a selection on non-Mac lets the browser copy, then sends `<Esc>` (`cm6:1480-1484`, `1518-1537`). [–]
- MD-07 `<C-o>` in Insert runs one Normal command and returns to Insert. The mode label shows `(C-O)` (`core:3426-3439`; `cm6:1429`). [–][E]
- MD-08 A selection made outside Vim (mouse, IDE command) enters Visual char. Losing the selection leaves Visual (`core:6888-6942`). [–][E] (`mouse_select`)
- MD-09 Readonly: `enterInsertMode` refuses (`core:3051`). The adapter drops changes (`cm6:82-83`). [–]
- MD-10 After a handled key, if Visual mode and "something selected" disagree, the engine resyncs (`core:7156-7158`). [–]
- MD-11 An exception inside a command resets the editor's Vim state and rethrows (`core:1056-1063`). [–]
- MD-12 In Normal and Visual, a printable key with no match is swallowed. A non-printable key with no match (`<C-s>`, `<Tab>`, `<F5>`) falls through to the editor (`core:1035-1036`). On macOS `<A-x>` is also swallowed. [–]
- MD-13 `vim-mode-change` fires for every transition above. `gn` from Normal fires `{mode:"visual", subMode:""}` (`core:2263-2331`). [W]

### 2.2 Counts and repeat (CT)

- CT-01 Count prefix `[1-9][0-9]*`. `0` alone is a motion (`core:1003-1030`). [–][E]
- CT-02 The count before an operator multiplies the count before its motion (`2d3w` = 6) (`core:1316-1353`). [–][E] (`dd_multiply_repeat`)
- CT-03 `explicitRepeat` motions (`G`, `gg`, `<C-d>`, `<C-u>`) tell "no count" from "1" (`core:2028-2034`). [–][E]
- CT-04 An operator typed twice is linewise over `count` lines (`dd`, `yy`, `cc`, `>>`, `g~g~`, `gUU` via `operatorShortcut`) (`core:1664-1672, 1010-1012`). [W][E]
- CT-05 `.` repeats the last edit: the action, or the operator with its motion, then replays the recorded insert-mode text (`core:3534-3544, 6972-7020`). [–][E] (`._*`)
- CT-06 `.` with a count replaces the original count and is remembered for later `.` (`core:3536-3542`). [–][E] (`._repeat`)
- CT-07 `o`/`O` with a count interleave command and insert (`interlaceInsertRepeat`, `core:214-215, 6996-7001`). [–][E] (`._insert_o_repeat`)
- CT-08 An Insert count (`3ix<Esc>`) repeats the inserted text on exit (`core:6693-6697`). [–][E] (`i_repeat`)
- CT-09 A count on `:` pre-fills `.,.+N-1` (`core:1989-1993`). [–]
- CT-10 A count on `v`/`V` selects `count` characters (`core:3136-3141`). [–]

### 2.3 Motions (MO)

Kinds: "excl" = exclusive charwise, "incl" = inclusive charwise, "line" = linewise. These apply when the motion follows an operator (`core:2155-2185`). Forward charwise motions under an operator are clipped to the line when the span ends in `\n` plus blanks (`clipToLine`, `core:3977-4004`). Linewise spans grow to whole lines (`core:4006-4011`). The Normal-mode caret is clipped to the last character of the line, never past it, and to the line end only in Insert or Visual (`clipCursorToContent`, `core:3571-3589`). A caret on the low half of a surrogate pair is pushed off it.

- MO-01 `h`/`l`, `<Left>`/`<Right>`, `<BS>`/`<Space>`: excl. They stop at the line edges, never wrapping (`core:2393-2398`). `dl` at EOL deletes the last character. [W][E]
- MO-02 `j`/`k`, `<Down>`/`<Up>`, `<C-n>`/`<C-p>`, `<CR>` (= `j^`): line. They keep the goal column `lastHPos` across `j k gj gk <C-d> <C-u> | $` (`core:2399-2441`). On the last line `j` goes to EOL and on the first line `k` goes to column 0: neither fails, unlike Vim (`core:2399-2441`). A fold is jumped over through `findPosV`, i.e. editor vertical motion (`cm6:504-531`). [–][E] (`j_with_folding`)
- MO-03 `gj`/`gk`, `g<Down>`/`g<Up>`: display lines, by pixel goal column, stopping at the document edge (`hitSide`) (`core:2442-2463`). The webview's editor has a Soft-Wrap toggle (`src/editor/core/gutterMenu.ts:45`; `src/editor/core/cm/verticalMotion.ts:35`). Hypothesis: the native editor does not soft-wrap (`grep -n wrap app-gpui/src/editor/view.rs` finds no wrapping code), so these differ from the webview whenever soft wrap is on. [–][E]
- MO-04 `0`, `<Home>`: excl (`core:2564`). `^`: first non-blank, excl, or EOL for a blank line (`core:4013-4019`). `g0`, `g^`, `g$`: display-line start and end (`core:2575-2583`; `cm6:388-396`). [–][E]
- MO-05 `$`, `<End>`: incl. A count moves `count-1` lines down. Sets the goal to infinity, so later `j` stays at EOL (`core:4432-4444`). [–][E] (`keepHPosEol`)
- MO-06 `+`, `-`, `_`: line, to the first non-blank. `_` uses count−1 (`core:143-145`). [–][E]
- MO-07 `|`: column `count-1`, clipped (`core:2523-2528, 4469-4479`). [–][E]
- MO-08 `w W b B`: excl. `e E ge gE`: incl. Empty lines count as words except for `e` (`core:4381-4430`). Word characters are `[\w\p{Alphabetic}\p{Number}_]` (`cm6:72-78`). Punctuation runs are words (`core:356-359`). `W`/`B` split on whitespace only. At the end of the document they stop at the last character, not erroring. [W][E]
- MO-09 `cw`/`cW` trims trailing whitespace from the deleted span (Vim's `cw` = `ce` rule, done by trimming) (`core:2724-2730`). [W][E]
- MO-10 `f t F T` + char: `f` and `t` are incl, `F` and `T` excl. Search the current line only. `t` stops one before. A failed `f` keeps the caret; a failed `t` makes the motion fail (`core:2501-2516, 4451-4467`). [W][E]
- MO-11 `;` and `,` repeat the last `f t F T`. `;` with `t` steps over an adjacent match (`core:2681-2695`). [W][E]
- MO-12 `gg`/`G` with or without a count: line, first non-blank, into the jump list (`core:2567-2574`). [–][E]
- MO-13 `H M L`: line, first non-blank of the top, middle or bottom visible line, with 6 px and 10 px occlusion tolerances. A count offsets from top or bottom (`core:2215-2227, 5566-5575`). [–][E] (`HML`)
- MO-14 `{ }`: excl, to the next empty-line boundary, into the jump list (`core:2472-2475, 4523-4545`). [–][E]
- MO-15 `( )`: sentences, ends `.?!` (`core:2476-2479, 4741-4916`). [–][E]
- MO-16 `%`: incl. The first bracket at or after the caret on the line, skipping brackets in string or comment tokens. Brackets are `(){}[]` only: the `<>` branch tests a symbol that `isMatchableSymbol` (`core:375-377`) never returns, so it is dead code. The match comes from the syntax-aware `matchBrackets` (`core:2540-2563`; `cm6:346-358`). [–][E] (`%_skip_string`, `%_skip_comment`)
- MO-17 `[( [{ ]) ]}` unmatched brackets, `[[ ]] [] ][` section braces at column 0, `[m ]m [M ]M` method braces, `[* ]* [/ ]/` comment ends, `[# ]#` `#if/#else/#endif` (`core:4152-4307`). [–][E]
- MO-18 `` `x `` (charwise excl) and `'x` (line) to a mark, into the jump list. `` `' `` and `''` go to the previous jump. `` `. `` goes to the last change end (`core:2332-2338, 5577-5600`). [–][E]
- MO-19 ``]` [` ]' ['``: next or previous lowercase mark, with a count (`core:2350-2392`). [–][E] (`jumpToMark_*`)
- MO-20 `n N`: next or previous match of the last search, honouring the search direction. They wrap around the document silently. With no query they do nothing. "No match found …" when absent (`core:2234-2262, 5444-5487`). [–][E]
- MO-21 `gn gN`: select the next or previous match, entering Visual. With an operator they act on the match (`core:2263-2331, 5489-5521`). [–][E]
- MO-22 `<C-f> <C-b>`, `<PageDown> <PageUp>`: by page, via editor vertical motion by the viewport height (`core:2464-2471`; `cm6:504-531`). [–][E] (`page_motions`)
- MO-23 `<C-d> <C-u>`: half a screen of display lines by default, or count lines. They also scroll by the same pixel delta (`core:2480-2496`). The count is not remembered as Vim's `scroll` is. [–][E] (`scrollMotion`)
- MO-24 `o` and `O` in Visual: go to the other end. `O` in block goes to the other corner on the same line (`core:2339-2349`). [–][E]
- MO-25 Operator-pending motions refuse actions (`core:3624-3627`). The engine has no `v`/`V`/`<C-v>` force-motion modifiers in operator-pending mode (nothing in the keymap at `core:75-262`). [–]
- MO-26 The engine has no fold commands: no `zo zc za zM zR zj zk` in the keymap (`core:75-262`). Folds matter only to MO-02. [–]

### 2.4 Operators (OP)

Every operator works with any motion (MO), any text object (TO), a count (CT-02) and Visual char, line and block (VI). It writes to the register given by `"x`, or else the default registers (RG-02).

- OP-01 `d`: delete. Linewise delete of the last line removes the preceding line break (`core:2766-2774`). Afterwards the caret goes to the first non-blank (linewise) or the start, then is clipped. Block: deletes each row's span (`core:2758-2791`). [W][E]
- OP-02 `c`: change, then Insert. Linewise `cc` keeps the indentation and leaves one line (`core:2732-2737`). Visual `R`/`S` changes whole lines (`fullLine`, `core:2740-2746`). Block `c` deletes the columns and inserts on every row (`core:2747-2752`). [W][E]
- OP-03 `y`: yank. The caret goes to the start of the span. Shows "N lines yanked [into "x]" for 1.5 s (`core:2899-2911`). [W][E]
- OP-04 `>` and `<`: indent the lines by one unit through the editor's indent-more or indent-less. In Visual the count repeats the shift. In block mode, the indent text is inserted or removed at the block's left column on each row (`core:2792-2850`; `cm6:364-379`). [–][E] (`>{motion}`, `><visualblock`)
- OP-05 `=`: re-indent the lines with the editor's language indentation (`core:2851-2854`; `cm6:779-781`). [–][E]
- OP-06 `g~ gu gU`, Visual `~ u U`, Normal `~` (one char, moves right): case operators. `g?` is rot13 (`core:2868-2944`). [–][E]
- OP-07 `gc`: toggle line comment over the lines (`core:2864-2867`; `cm6:767`). [–][E] (`gcc`)
- OP-08 `gq` and `gw`: hard wrap at `textwidth`, merging short lines. `gw` keeps the caret. See OP-13 and OPT-02 for the width actually used (`core:2855-2863`; `cm6:1014-1090`). [–][E] (`gq_and_gw`)
- OP-09 `x X D C Y s S`: operator+motion shortcuts (`dl`, `dh`, `d$`, `c$`, `yy`, `cl`, `cc`). In Visual, `D C Y` act linewise and `X` makes the selection linewise first (`core:187-200`). [W][E]
- OP-10 `J` and `gJ`: join `max(count,2)` lines, collapsing the next line's leading blanks to one space (`gJ` keeps them). In Visual, join the selected lines (`core:3190-3231`). [–][E]
- OP-11 `r<char>`: replace `count` characters (clipped to the line), or the whole Visual or block selection. `r<CR>` breaks the line (`core:3444-3494`). [–][E]
- OP-12 A linewise operator in Normal mode over a single line returns the caret to the first non-blank (`core:2891-2896`). [–]
- OP-13 `gq` uses `options.column || cm.getOption('textwidth') || 80` (`cm6:1016`). The adapter's `textwidth` is a per-editor value set only by `:set tw=` in that editor (`core:540-555`; `cm6:679-702`). [–]

### 2.5 Text objects (TO)

`i` and `a` followed by a character, after an operator or in Visual (`core:251-252, 2585-2679`).

- TO-01 `iw aw iW aW`: `aw` takes trailing blanks, else leading ones. `iw` on blanks selects the blank run. A count extends by words, across lines (`core:4026-4118`). [W][E] (`diw_*`, `daw_*`, `w_text_object_repeat`)
- TO-02 `i( a( ib ab i) a)`, `i{ a{ iB aB i}`, `i[ a[ i]`, `i< a< i>`: multi-line through a bracket scan (1,000 lines at most, string and comment brackets included). If the caret is not inside a pair, the next opening bracket forward is used (`core:2617-2627, 4918-4962`; `cm6:929-959`). [–][E]
- TO-03 `i' a' i" a" ` i` a` `: current line only. `a` takes the quotes but no surrounding blanks, unlike Vim. A string token decides whether a quote under the caret opens or closes (`core:4964-5024`). [–][E]
- TO-04 `ip ap`: paragraph, always linewise (`core:2585-2679, 4523-4584`). [–][E] (`paragraph_motions`)
- TO-05 `is as`: sentence (`core:2659-2670, 4585-4740`). [–][E] (`sentence_selections`)
- TO-06 `it at`: XML/HTML element from the syntax tree's `OpenTag`/`CloseTag` nodes. With no tree it is a no-op (`core:4120-4136`; `cm6:961-985`). [–][E] (`dat_*`, `dit_*`)
- TO-07 In Visual, a text object extends the selection (`expandSelection`, `core:3841-3869`). A paragraph makes it linewise. [–][E]

### 2.6 Registers (RG), marks (MK), macros (MA), jump list (JL)

- RG-01 Valid registers: `a-z`, `A-Z` (append), `0-9`, `-`, `"`, `.`, `:`, `_`, `/`, `+`, plus `\w` in general (`core:360-361, 1535-1537`). An invalid name (`*`) falls back to the default behaviour. [–][E]
- RG-02 With no register: a yank sets `0`. A delete or change with no newline sets `-`. A multi-line delete or change shifts `1→2…8→9` and sets `1`. The unnamed register always follows (`core:1474-1502`). [W][E]
- RG-03 A named register: lowercase replaces, uppercase appends. Linewise-ness is merged (`core:1388-1396, 1509-1514`). Unnamed is then set to the register's content. [–][E] (`yank_append_*`)
- RG-04 `"_` is the black hole: nothing is stored, not even unnamed (`core:1474`). [–][E]
- RG-05 `"+` is the system clipboard. It writes through and reads asynchronously on paste (`core:1516, 3254`). No `"*`, no `clipboard=unnamed`. The unnamed register is never synchronised with the system clipboard. [–]
- RG-06 Read-only registers: `.` (last inserted text, `core:6709`), `:` (last Ex line; `:registers` and `:marks` do not overwrite it, `core:5627-5657`), `/` (last search, `core:5240`). [–][E] (`._register`, `:_register`, `search_register`)
- RG-07 `p P`: after or before. Linewise text goes below or above the line, and the caret goes to the first non-blank of the first pasted line. Charwise text with `p`: the caret ends on the last pasted character. With `P` it ends one further, on the character that was under the caret (`core:3394-3397`; the suite asserts it: `suite:2109-2111`), unlike Vim, where `P` also ends on the last pasted character. Multi-line charwise: the caret goes to the start of the pasted text. A count repeats the text (`core:3262-3405`). [W][E]
- RG-08 `]p [p`: paste matching the current line's indentation, tabs or spaces (`core:3262-3300`). [–][E]
- RG-09 Blockwise paste: one row per line, padding short lines with spaces and adding lines at the end of the document (`core:3262-3405`). [–][E] (`blockwise_paste*`)
- RG-10 Paste in Visual replaces the selection. The unnamed register then holds the replaced text (`core:3262-3405`). [–][E] (`visual_paste`)
- RG-11 `<C-r>x` in Insert inserts a register (`core:3418-3425`). [–][E] (`<C-r>_insert_mode`)
- RG-12 `:registers [names]` lists non-empty registers in a long message (`core:6052-6076`). [–][E]
- MK-01 `m{a-zA-Z0-9_<>}` sets a mark on this editor. Marks are bookmarks that follow edits (`core:3440-3443, 4481-4495`). Uppercase marks are not global across files, unlike Vim. [–][E]
- MK-02 `'<` and `'>` are kept by every Visual change (`core:2082-2087, 3149-3150`). [–][E] (`visual_marks`)
- MK-03 `` `. `` and `'.` are the end of the last change in this editor (`core:5583-5600`; `cm6:597-599`). [–][E] (`mark.`)
- MK-04 `:marks [names]` (`core:6077-6100`) and `:delmarks a b-d` (ranges within one case, `core:6463-6523`). There is no `:delmarks!`. [–][E] (`delmark_*`)
- MK-05 `gv` reselects the last Visual selection (bookmarked, follows edits). After a Visual paste the reselection covers the pasted text (`core:3162-3189, 3824-3840`). [–][E] (`reselect_visual*`)
- MA-01 `q{reg}` records and `q` stops. "recording @x" shows in the panel (`core:659-697, 3032-3038, 918-931`). [–][E]
- MA-02 The recording holds keys plus each insert session's text changes plus `/` queries, kept apart (`core:1378-1433, 6803-6836`). [–][E] (`macro_*`)
- MA-03 `@x` replays with a count. `@@` replays the last one. `@:` repeats the last Ex line (`core:3019-3031, 6768-6801`). [–][E] (`@@`, `macro_last_ex_command_register`)
- MA-04 A macro replay disables `.` recording and search prompts (it takes the recorded queries) (`core:1748-1908, 2199-2208`). [–][E]
- JL-01 The jump list is a ring of 100 bookmarks. Motions with `toJumplist` (`H M L G gg % { } n N * # / ? ' `` ` ``) add entries (`core:557-641, 2048-2056`). [–][E] (`jumplist_*`)
- JL-02 `<C-o>` and `<C-i>` walk the list with a count, skipping deleted marks. They are disabled in Visual (`core:2952-2964`). [–][E]
- JL-03 `*`/`#` record the position from before the word-start adjustment (`cachedCursor`, `core:1897, 2048-2056`). [–][E]

### 2.7 Search and substitution (SR)

- SR-01 `/` and `?` open the prompt with prefix `/` or `?` and a clickable "(JavaScript regexp: set pcre)" label that toggles `pcre` (`core:1748-1880`). [–]
- SR-02 Incremental: each key re-parses the query, scrolls to the next match and highlights it. An invalid regex clears the highlight and restores the scroll. `<Esc>`, `<C-c>`, `<C-[>` or `<BS>` on an empty prompt restore the previous query and scroll (`core:1795-1850`). [–][E]
- SR-03 Prompt history: `<Up>`/`<Down>` filter by the typed prefix. `<C-u>` clears (`core:1547-1590, 1795-1850`). [–][E] (`search_history`)
- SR-04 Case: prompt searches are smartcase (ignore case unless the pattern has `[A-Z]`). `*`, `#`, `g*`, `g#` and macro replays always ignore case. A trailing `/i` forces ignore case (`core:1776-1780, 1900, 5237-5279`). [–][E] (`/_case`)
- SR-05 Dialect: with `pcre` on (the default, `core:5026`), the pattern is a JavaScript `RegExp` source with flag `m` (and `i`). With `nopcre`, Vim magic is translated (`core:5107-5156`): `\v \m \M \V` modes, `\< \>` become lookarounds, `\zs` becomes a lookbehind, `\ze` a lookahead, `\(` `\|` `\{` `\+` `\?` unescaped. The searcher escapes bare `{`/`}` that are not quantifiers (`cm6:427-437`) and matches through CodeMirror's `RegExpCursor`. That cursor matches line by line, except that a pattern containing `\s`, `\W`, `\D`, `\n`, `\r`, a literal line break or `[^` switches to a multi-line cursor (`node_modules/@codemirror/search/dist/index.js:166-167`). A native implementation must take JavaScript syntax and semantics (lookbehind, backreferences `\1`, named groups, `\d`/`\w` ASCII-only, `\s`, `$` with `m`, the `i` flag's case folding) as it is the default. [–][E] (`/_2_pcre`, `/_2_nopcre`, `/_nongreedy`, …)
- SR-06 `* #`: the keyword under or after the caret, as `\bword\b`. With no keyword, the non-keyword run escaped. `g* g#` without `\b`. The caret goes to the word start first. "No word under cursor" (`core:1874-1907`). [–][E]
- SR-07 Highlighting: after any search all matches are highlighted (a 50 ms debounce), in the visible ranges; visible ranges closer than 500 document offsets (2 × `HighlightMargin` = 250) are merged into one (`core:5418-5442`; `cm6:1302, 1444-1459`). It is cleared by `:noh`, by `<Esc>` in Normal (`cm6:1470-1478`), and by closing an Ex prompt (`core:1911-1930`). [–][E] (`ex_noh_clearSearchHighlight`)
- SR-08 The search state (query, direction) is global across editors (`core:5029-5058`, through `vimGlobalState`). [–]
- SR-09 `:s/pat/rep/[gci] [count]` with any separator. An empty pattern reuses the last search. An empty replacement reuses the last replacement. `%` or `1,$` reaches to EOF even if lines are added (`core:6307-6391`). [–][E] (`ex_substitute_*`)
- SR-10 Replacement syntax. pcre: `$1`, `$&`, `&` → whole match, `\/ \\ \n \r \t \&` (`core:5198-5226, 6325`). nopcre: `\1`→`$1`, `\n` etc. (`core:5160-5196`). `$n` with n beyond the groups is truncated digit by digit (`core:6567-6576`). [–][E]
- SR-11 Without `g`, one replacement per line. Matches made after joining lines are handled (`joined`). A zero-length match next to the previous one is skipped (`core:6587-6610`). [–][E] (`ex_substitute_newline_*`, `ex_substitute_empty_match`)
- SR-12 `c` flag: the prompt "replace with X (y/n/a/q/l)". `y` replaces, `n` skips, `a` replaces all, `l` replaces and stops, `q`/`<Esc>` stop. Other keys are ignored. Each match is selected and scrolled into view (`core:6632-6662`). [–][E] (`ex_substitute_confirm_*`)
- SR-13 Messages: "Found N matches for pattern: …", "No matches for …", plus "(set nopcre to use Vim regexps)" (`core:6625-6629, 6666`). [–]
- SR-14 `:g/pat/cmd`, `:g!/pat/cmd`, `:v/pat/cmd`: run `cmd` on each matching line by line handle, so that deletions and joins are followed. With no `cmd`, list the lines in a message (`core:6235-6305`; `cm6:241-260`). [–][E] (`ex_global*`)
- SR-15 The `/` register holds the last query. Searching sets it (`core:5238-5239`). [–][E]

### 2.8 Insert-mode and Replace-mode keys (IN)

- IN-01 Typing, `<CR>`, `<BS>`, `<Del>`, `<Tab>` and arrows in Insert are the editor's own keys. Only the keys below are the engine's (the insert-context entries at `core:95-98, 197-198, 237-249`). [W]
- IN-02 `<C-w>`: delete the word before the caret (`moveByWords` back). `<C-u>`: delete to column 0 (`core:197-198`). [–][E]
- IN-03 `<C-t>` and `<C-d>`: indent or unindent the line (`core:248-249, 3545-3547`). [–][E]
- IN-04 `<C-r>{reg}`: see RG-11. `<C-o>`: see MD-07. `<C-[>`, `<C-c>`: Esc. `<Ins>`: see MD-03. [–][E]
- IN-05 Insert-mode mappings (`inoremap jk <Esc>`): a printable key that starts a mapping is inserted at once. When the mapping completes, the inserted keys are removed again at every caret. After 200 ms (`insertModeEscKeysTimeout`) the pending keys are kept as text (`core:950-992`). [W][rc]
- IN-06 A mapping right-hand side that types text in Insert inserts it literally. `<lt>`, `<Space>` and `<CR>` become characters. Arrow and editing keys run the editor's key (`core:1161-1186`; `cm6:117-124`). [W][rc] (`inserts escaped key notation literally`)
- IN-07 Recording the insert session for `.` and macros: text from typing or paste (`+input`/`paste` origins) and `<BS>`/`<Del>` keys. A caret move inside the session resets the recording (`core:6838-6886, 6888-6906, 6944-6970`). [–][E]
- IN-08 `a` and `i` with surrogate pairs step over the whole pair (`core:3062-3066`). [–][E]
- IN-09 `I`/`A` in Visual char: `I` goes to the start (or the column 0 of the anchor line), `A` to after the end (`core:3068-3101`). [–][E] (`A_endOfSelectedArea`)
- IN-10 `gi` returns to the last change end (`core:3102-3104`). `gI` goes to column 0. `I` goes to the first non-blank. [–][E]
- IN-11 `o`/`O`: a new line with the editor's newline-and-indent. `O` on line 0 inserts a line at the top (`core:3232-3249`). [–][E] (`._insert_o_indent`)
- RP-01 Replace typing overwrites one character per key and never the line break (`cm6:1489-1499, 721-737`). [–][E] (`R`)
- RP-02 `<BS>` in Replace only moves left. It does not restore the replaced character, unlike Vim (`cm6:1494-1497`). [–][E] (`i_overwrite_backspace`)
- RP-03 Visual `R` changes the selected lines (OP-02). `R` with a count repeats on exit (`core:229-230`). [–][E] (`R_visual`, `._replace_repeat`)
- RP-04 Hypothesis: a paste or IME commit in Replace mode inserts rather than overwrites, because the overwrite path is only in the keydown handler (`cm6:1489-1499`). Settle with a webview test that pastes in Replace mode. [–]

### 2.9 Visual char, line and block (VI)

- VI-01 `v V <C-v> <C-q>` enter, switch between kinds, or leave when the same key is pressed again (`core:3128-3161`). [W][E] (`visual_block_mode_switch`)
- VI-02 Mapping to the editor's selection. Char: the selection includes the character under the head. Line: from column 0 to the line end. Block: one range per row from `min(ch)` to `max(ch)+1`, main range on the head row (`core:3886-3937`). Columns are UTF-16 code units, not display columns, so tabs are one column. [–][E]
- VI-03 The caret is drawn on the last selected character when the anchor is before the head (`cm6:1231-1234`). [–][E] (`rendered_cursor_position_cm6`)
- VI-04 Crossing over the anchor keeps the anchor character selected (`core:3886-3897`). [–][E] (`visual_crossover_*`)
- VI-05 `$` in block extends every row to its own end (`newHead.ch === Infinity`, `core:2072`). Short rows are truncated (`core:3755-3790`). [–][E] (`visual_block_move_to_eol`, `visual_block_truncate_on_short_line`)
- VI-06 An operator in Visual applies to the selection and leaves Visual. The caret goes where the operator returns, or to the start (`core:2094-2197`). [–][E]
- VI-07 Block `I`: insert at the left column on every row. Block `A`: append after the right column on every row. Done as one caret per row, so the typing goes to all rows at once (`core:3068-3101, 3792-3800`). `.` replays it over the same height (`core:7036-7068`). [–][E] (`I_visual_block`, `A_visual_block`, `I_visual_block_replay`)
- VI-08 Block `c`, `r`, `~`, `d`, `y` and `p`, and blockwise registers (RG-09) (`core:2747-2752, 2777-2783, 3444-3494`). [–][E]
- VI-09 `:` in Visual pre-fills `'<,'>` (`core:1986`). [–][E] (`ex_substitute_visual_range`)
- VI-10 `<Esc>` leaves Visual and puts the caret on the head, clipped. It stores the last selection for `gv` (`core:3956-3975`). [–][E]
- VI-11 `gn` with Visual extends to the match (MO-21). [–][E]
- VI-12 `s` in Visual = `c`. `S` in Visual = `VdO` (`core:99-102`). [–][E] (`s_visual`, `S_visual`)
- VI-13 `J` joins the selected lines (OP-10). `<` and `>` with a count shift count times. [–][E]

### 2.10 Ex commands (EX)

The parser (`core:5602-5909`) handles all commands:

- EX-01 The line is parsed as `[range] name [args]`. Ranges: `%`, `*` (last Visual), `N`, `.`, `$`, `'x`, `/pat/`, `?pat?`, `\/`, `\?`, each with `+N`/`-N` offsets, `a,b`. With no range: the Visual `'<,'>` lines, or the caret line (`core:5693-5800`). [–][E] (`ex_advanced_range_syntax`)
- EX-02 A range alone (`:42`, `:'a`, `:.+3`) goes to that line (`move`, `core:5647-5650, 5969-5977`). [–][E] (`ex_go_to_*`)
- EX-03 A command name matches the longest registered prefix whose full name starts with what was typed (`core:5832-5842`). Command names are `\w+` or one of `!! @@ ! # & * < = > @ ~` (`core:5726`). [–]
- EX-04 Unknown: "Not an editor command ":…"". A parse error shows its message (`core:5636-5640, 5672`). [–]
- EX-05 The Ex history (separate from the search history) and the `:` register (RG-06) (`core:1914`). [–][E] (`exCommand_history`)
- EX-06 The IDE's commands (A8). `w wa q qa wq x action` run IDE actions after the key handling (`ts:engine.ts:265-303`). [W]
- EX-07 `:set opt`, `:set noopt`, `:set opt!`, `:set opt?`, `:set opt=val`, `:setlocal`, `:setglobal`. Only the first argument is read. Errors show "Unknown option: x" or "Invalid argument" (`core:5979-6051`). [rc][E] (`set_*`, `ex_set_*`)
- EX-08 `:map :nmap :vmap :imap :omap :noremap :nnoremap :vnoremap :inoremap :onoremap lhs rhs`. `:map :x :y` maps one Ex command to another and `:map :x keys` maps an Ex command to keys (`core:5852-5885, 5921-5948`). [rc][E] (`ex_map_*`, `ex_nmap`, `ex_imap`, `ex_omap`)
- EX-09 `:unmap lhs` removes the first entry with those keys and context, defaults included. "No such mapping" otherwise (`core:5887-5908, 5950-5958`). [rc][E] (`ex_unmap_*`)
- EX-10 `:mapclear` and `:nmapclear :vmapclear :imapclear :omapclear`. A per-context clear re-adds context-less mappings for the other contexts (`core:849-875`). [rc][E] (`mapclear*`)
- EX-11 `:sort[!] [dinuoxr] [/pat/]` (`core:6101-6199`). Quirk: a range starting on line 0 is treated as no range (`params.line || firstLine`, `core:6131`). [–][E] (`ex_sort_*`)
- EX-12 `:s` and `:g`/`:v`: see SR-09 to SR-14. [–][E]
- EX-13 `:normal[!] keys` over a range or the caret line. It leaves Insert at the end (`core:6205-6233`). [–][E] (`ex_normal`)
- EX-14 `:yank [reg]` (default `0`), `:put[!] [reg]`, `:delete`, `:join` over the range (`core:6412-6461`). [–][E] (`ex_yank`, `ex_delete`)
- EX-15 `:noh`, `:startinsert[!]`, `:undo`, `:redo`, `:registers`, `:marks`, `:delmarks`, `:colorscheme` (which does nothing in CodeMirror 6, `cm6:679-689`), `:version` (`core:6393-6411, 6527-6529`). [–][E]
- EX-16 `:write` is the engine's own, but the IDE's `defineEx('write','w')` replaces it (A8). [W]

### 2.11 Options (OPT)

The engine defines exactly five options. `:set` of any other name fails with "Unknown option".

- OPT-01 `filetype`/`ft`: local. It proxies to the editor's mode option, which the CodeMirror 6 adapter ignores (`core:526-539`; `cm6:679-702`). [–][E] (`ex_set_filetype*`)
- OPT-02 `textwidth`/`tw` (default 80): local only. The global set the rc uses (`Vim.setOption(name, value)` with no editor, `ts:engine.ts:368`) reaches the callback with no editor, which returns at once (`core:540-555`). An rc `set tw=100` therefore has no effect in the webview, and `gq` keeps wrapping at 80. A native port must either reproduce this or the difference must be recorded as a deliberate fix. [rc]
- OPT-03 `pcre` (boolean, default on): the search dialect (SR-05). [rc][E]
- OPT-04 `insertModeEscKeysTimeout` (default 200 ms): IN-05. [rc]
- OPT-05 `langmap`/`lmap`: a remap of typed characters in Normal and Visual, in the forms `ab;cd`, `aAbB` and pairs with escapes. Ctrl keys are remapped too unless `remapCtrl` is false (`core:1262-1313, 1240-1242`). [rc][E] (`set_langmap`)

### 2.12 Command line and messages (CL)

- CL-01 One bottom panel per editor, shown only while a prompt or message is open (`cm6:1650-1671, 1352-1361`). [–]
- CL-02 The prompt is a prefix (`:`, `/`, `?`, or the `:s///c` text) plus a text input that takes focus. Enter submits, Escape closes, blur closes (`cm6:868-924`; `core:5316-5348`). [–]
- CL-03 Short messages show in red, for 15 s by default, until clicked or replaced (`core:5299-5314`; `cm6:823-845`). [–]
- CL-04 Long messages (`:registers`, `:marks`, `:g` with no command) stay until dismissed, with "Press ENTER or type command to continue". The next key closes them, and `<CR>` is then consumed (`core:5302-5308, 7099-7107`). [–][E] (`registers_html_encoding`)
- CL-05 Keys sent by a mapping or `:normal` while a prompt is open go to a virtual prompt, not the DOM (`core:1094-1140, 5328-5332`). For example `nnoremap <leader>s :s/a/b/<CR>`. [rc][E] (`map_prompt`)
- CL-06 While a confirm prompt for `:s///c` is open, it takes the keys (SR-12). [–][E]
- CL-07 The "recording @x" indicator shows in the panel while recording (`core:688`). [–]
- CL-08 The IDE shows no pending-keys text. The adapter keeps `vim.status` (`cm6:1485`), but `updateStatus` returns at once when there is no status bar (`cm6:1414-1418`), and the status bar exists only with the `status` option (`cm6:1672-1686`), which the IDE does not pass (`ts:engine.ts:256`). The only visible sign of pending keys is the half-height block caret (`cm6:1238`). [–]

### 2.13 Scrolling and screen motions (SC)

- SC-01 `<C-e>` and `<C-y>`: scroll by count lines, keeping the caret on screen (moving it if needed). Disabled in Visual (`core:2965-3001`). [–][E]
- SC-02 `zz`, `z.`, `zt`, `z<CR>`, `zb`, `z-`: put the caret line at the centre, top or bottom. The dot, `<CR>` and `-` forms also go to the first non-blank (`core:239-244, 3002-3018`). [–][E] (`zb_*`, `zt_*`, `zz_*`)
- SC-03 After every Vim operation that moved the caret, the caret is scrolled into view (`cm6:653-669`). [–]
- SC-04 `H M L <C-d> <C-u> <C-f> <C-b>`: see MO-13, MO-22, MO-23. [–][E]
- SC-05 `<C-a>` and `<C-x>`: add or subtract count to the number at or after the caret on the line. Accepts `-`, `0x` hex, `0b` binary and a leading `0` as octal, keeps the zero padding, and ends on the number's last digit (`core:3495-3533`). [–][E] (`increment_*`)

### 2.14 Multiple cursors (MC)

- MC-01 With more than one selection range, each key runs once per range against a clone of the Vim state, inside one operation. The insert-mapping change queues are kept per range (`core:7091-7156`; `cm6:738-757`). [–]
- MC-02 Visual block is exempt from MC-01: its ranges belong to it (`core:7097, 7120`). [–]
- MC-03 `<Esc>` in Normal with several ranges, when the last key was `<Esc>`, lets the editor collapse them (`core:7116`). [–]
- MC-04 Insert-mode typing at several carets is the editor's own. Hypothesis: `.` replays at the main caret only; settle with a webview test of `.` after a multi-caret insert. [–]

### 2.15 IME and key notation (KY)

- KY-01 Key notation: `<C-x>`, `<A-x>`, `<M-x>` (Meta/Cmd), `<S-x>` only with another modifier or a named key, and the names `CR BS Del Esc Ins Left Right Up Down Space Home End PageUp PageDown Tab F1-F12`. Numpad keys lose their `Numpad` prefix (`core:1201-1260`). [W][rc]
- KY-02 On macOS a lone `Alt` with a one-character key drops the `A-` (Option composes characters) (`core:1234`). [–]
- KY-03 A non-ASCII key not used by any mapping is replaced by the last letter of its physical key code (`KeyA` → `a`), so that Normal commands work on non-Latin layouts (`core:1243-1251`). [–]
- KY-04 `<character>` and `<register>` slots take the next key, which must be a single character, else the command is cleared (`core:1611-1615, 3641-3655`). A `<character>` slot sets `expectLiteralNext`, which bypasses langmap (`core:1606-1607`). [–][E]
- KY-05 Matching: among the entries for the current context, the first full match in keymap order wins over any partial match. User entries sit in front (`core:1599-1617, 3618-3640, 6717-6721`). Contexts: `insert` matches only insert entries, operator-pending replaces the context while an operator is pending, and context-less entries match every non-insert context. [W][rc]
- KY-06 `noremap`: while a non-recursive mapping's right-hand side runs, only the default region of the keymap is searched (`core:1088, 1143-1149, 3621`). [W][rc] (`noremap*`)
- KY-07 Key-to-key recursion through `doKeyToKey`. A mapping already on the stack is not re-entered (`core:1142-1199`). [rc][E]
- KY-08 IME in Normal (the adapter's part): a composition's single-character commit is treated as one key and the composition is force-ended (`cm6:1555-1600, 1616-1648`). A dead key's `keypress` is handled (`cm6:1543`). The IDE's part is A3 to A5 and `ts:engine.ts:29-179`. [W]
- KY-09 Paste in Normal or Visual (a DOM paste event): the caret moves one right and the editor enters Insert, so that the clipboard text is inserted after the caret (`core:326-327, 341-353`). [–]
- KY-10 `<C-c>` copy rule: see MD-06. [–]

## 3. The minimum for parity, and why it is the whole engine

The checklist has 184 items in 19 groups (counted with `grep -cE "^- [A-Z]+-[0-9]+ "` over section 2 only): MD 13, CT 10, MO 26, OP 13, TO 7, RG 12, MK 5, MA 4, JL 3, SR 15, IN 11, RP 4, VI 13, EX 16, OPT 5, CL 8, SC 5, MC 4, KY 10. Many items bundle several keys (MO-17 alone is twelve keys). Measured from `suite`, the engine's own suite has 697 cases (444 `testVim`, 80 `testEdit`, 67 `testMotion`, 34 `testSubstitute`, 23 `testJumplist`, 19 `test`, 14 `testSubstituteConfirm`, 10 `testSelection`, 4 `testCursorPosition`, 2 `testMotionWithFolding`). 136 of the 184 items have cases there. Only 28 items are touched by the IDE's own tests, and 15 depend directly on the rc feature.

1:1 parity with the webview means the engine's whole behaviour, quirks included, because a user of the webview build can type any of it. The IDE's tests are not the bar: they cover about 15 behaviours, while the keymap alone has 174 entries (`core:75-262`, counted by `grep -c "{ *keys:"`). The honest minimum is therefore everything in section 2. Two exceptions are recorded below, each as a deliberate, owner-visible decision.

Items rarely used enough to list as "not built first" (built last, in their slice's tail, or recorded as a gap if the owner agrees):

- OPT-01 `filetype` (a no-op in the webview except for reading the value back) and EX-15 `:colorscheme` and `:version`.
- OPT-05 `langmap` and KY-03, the non-Latin layout fallback. The fallback needs a physical key code, which GPUI's keystroke does not carry (risk R2).
- MO-17 `[m ]m [M ]M [* ]* [/ ]/ [# ]#`.
- OP-06 `g?` (rot13), and SC-05's octal and binary forms.
- TO-06 `it at`. This needs element nodes from a syntax tree. The native editor has no tag helper (`grep -n -i tag app-gpui/src/editor/structure.rs` finds none). Hypothesis: the backend's syntax tree has element nodes for HTML and XML; settle by reading `crates/ide-syntax` before S7.
- EX-11's numeric `:sort` modes `x o`, and the `r` and `/pat/` options.
- CL-05, the virtual prompt for mappings that open `:` or `/`. It is rare in rc files except for `nnoremap <leader>x :s/…<CR>`. Note that `:<C-u>…<CR>` mappings already bypass it as `mapEx` (`ts:rc.ts:125-130`).
- SR-05's `nopcre` translation, if the regex decision (R1) is postponed.

Two items are candidates for a recorded deliberate difference, not a silent one: OPT-02 (`set tw` from the rc has no effect in the webview) and RP-02 (Replace-mode `<BS>` does not restore). Matching them is cheap; the decision is the owner's.

What a user notices missing at each stage of section 5:

- After S1–S5 and I1, I2a, I3: Normal-mode motions, operators, counts and undo work, with the mode shown and the rc applied. Missing: registers beyond unnamed, `p` variants, text objects (`ciw`, `di(`), Visual mode, `.`, search, the command line (so even `:w` waits for S12 and I2b). This is the first stage worth showing. It is most of what `vim.test.ts` touches.
- After S6–S10: everyday Vim is complete (registers, text objects, Insert keys, `.`, macros, marks, Visual char, line and block). Missing: `/` `?` `*` `n`, `:s`, `:g`, `:sort`, `:normal`, multi-cursor rules.
- After S11–S14 and I2b, I4: parity, less the items above.

## 4. The native design

### 4.1 Shape

The engine is a pure model in `app-gpui/src/features_a/vim/engine/` (beside the existing `rs:engine.rs`, which becomes `engine/ide.rs` or stays as is). It holds no GPUI types. The model is driven one key at a time:

- `VimEngine::handle_key(editor_state: &mut VimEditorState, global: &mut VimGlobal, key: &VimKey, host: &mut dyn VimHost) -> KeyResult`. `KeyResult` is one of `Handled`, `Pending`, or `Pass`. `Pass` means the editor's own handling runs, as in MD-12 and IN-01.
- `VimEngine::handle_ex(…, input: &str, host) -> ()`. The engine's Ex dispatcher calls back into the IDE commands (4.7).
- `VimEngine::text_input(…, text: &str, host) -> bool`, for text that arrives through the input handler instead of a key (KY-08, KY-09).

The state is split as the webview splits it. `VimGlobal` is one GPUI global holding: the registers, macro state, jump list, search query and direction, last character search, last substitute replacement, the two histories, the keymap (defaults plus user entries), and global option values (`core:762-784`, `core:1455-1545`). `VimEditorState` is one per editor, holding: input state, mode flags, `sel`, marks, last selection, `lastHPos`/`lastHSPos`, the last-edit input state, insert repeat, local options and status (`core:698-743`). The jump list is global, and each entry is a bookmark of the editor that recorded it: `Marker.find` answers a position in its own editor's document (`cm6:992-1007`). `<C-o>` then sets that position in the current editor (`core:2952-2964`). So after switching editors, `<C-o>` moves to a line and column recorded in another document. A native port keeps the entry's owner and reproduces this, or records a deliberate fix.

Positions are (line, UTF-16 column), as in the engine, converted at the host boundary with `buffer::line_col` and `buffer::offset_at` (`ed:buffer.rs:25,48`). A port can then follow the engine function by function, and the 697 suite cases (which assert `Pos`) can be transcribed directly.

### 4.2 The host trait (`VimHost`): what the engine needs from the editor

All offsets are UTF-16, as everywhere in the native editor (`ed:buffer.rs:1-5`).

- Text: `rope()` → `Editor::rope` (`ed:view.rs:761`). Line ranges, columns and slices come from the `buffer` helpers (`ed:buffer.rs:11-62`). Tab size and indent unit → `Editor::edit_state` (`ed:view.rs:881-890`).
- Selection: `selections()` and `main_index()` (`ed:view.rs:555,560`), and `set_selections(ranges, main)` (`ed:view.rs:938`). `set_selections` seals the undo history (`ed:view.rs:945`), and the engine sets selections in the middle of a command, so the host needs a variant that does not seal while a Vim operation is open (4.6).
- Edits: `replace(changes, selections, main)` → `Editor::apply_edit_from` (`ed:view.rs:1189`) with a new `EditOrigin::Vim`. Read-only refuses (`ed:view.rs:1197`), matching MD-09.
- History: `undo()` and `redo()` → `Editor::undo`/`redo` (`ed:view.rs:1238,1252`). After undo the engine puts the caret at the start of the change (`cm6:105-116`; `core:3406-3411`).
- Language commands: newline-and-indent → `editor_commands::indent::insert_newline_and_indent` (`app-gpui/src/editor_commands/indent.rs:151`). Re-indent → `core_actions::auto_indent` (`ed:core_actions.rs:393`). Line comment → `editor_commands::comments::comment_line` (`app-gpui/src/editor_commands/comments.rs:73`). Indent more and less: the native editor indents a selection only through Tab (`ed:view.rs:1468` → `smart_keys::insert_tab`, with the private `indent_lines` at `app-gpui/src/editor_commands/smart_keys.rs:39`). A grep of `app-gpui/src/editor_commands` for a public unindent function finds none, so `<`, `<<` and `<C-d>` need a new pure function there (S5).
- Tokens: "is this position in a string or comment" → `Editor::literal_tree` (`ed:view.rs:895`), for MO-16 and TO-03. Bracket matching → `bracket_marks` (`ed:extras.rs:148`) or the language facts. Element tags: Hypothesis, see TO-06.
- Viewport: top line → `Editor::top_line` (`ed:view.rs:586`). Painted lines → `painted_lines` (`ed:view.rs:638`). Line height → `ed:view.rs:746`. Scroll → `scroll_by` and `scroll_to_line` (`ed:view.rs:987,591`). Centre → `scroll_caret_to_center` (`ed:view.rs:850`). Page size → `page_lines` (`ed:view.rs:1825`, private today). Vertical motion that skips folds → `Editor::vertical`'s loop (`ed:view.rs:1659-1690`, private today). Folds → `Folds::is_hidden` and `row_of_line` (`ed:folds.rs:162,179`). The pure model takes these as plain numbers (top line, visible line count, line height). That keeps H/M/L and the scroll actions testable without a window.
- Clipboard: write and read text → `cx.write_to_clipboard` and `cx.read_from_clipboard` as `Editor::copy` and `paste` do (`ed:view.rs:1328,1346`), for `"+` only (RG-05).
- Bookmarks that follow edits (marks, the jump list, `gv`, the insert end) → `map_offset` (`ed:buffer.rs:177`). The host reports every edit's changes (`EditorEvent::Edited`, `ed:view.rs:297-301`) so the engine can map its bookmarks, as `cm6:601-628` does.
- UI: `show_message(text, long, duration)`, `open_prompt(prefix, initial, kind)`, `mode_changed(mode, sub)`, `run_ide_action(id)` (deferred until after the key, as `ts:engine.ts:265-268` does). These are implemented by the integration (4.8).

The test double is a `FakeHost` over `editor_commands::EditState` and `commands::apply` (`app-gpui/src/editor_commands/mod.rs:109`; used as at `ed:view.rs:1672`), with a fixed viewport. Every engine slice tests against it.

### 4.3 Key parsing

- A `VimKey` is the engine's notation string (`h`, `<C-d>`, `<S-Tab>`, `<Esc>`), parsed from a GPUI `Keystroke { key, modifiers, key_char }`. Printable keys come from `key_char` (shifted characters). Named keys map as KY-01, beside the IDE's own name map (`app-gpui/src/platform/input.rs:179-207`). The macOS `A-` rule (KY-02) uses `is_mac_host` (`app-gpui/src/platform/keymap.rs`).
- The rc side already produces this notation: `normalizeVimKeys` (`ts:rc.ts:75-103`) and its native port in `rs:rc.rs`, plus `split_keys` and `first_key` (`rs:engine.rs:98-119`). The parser and the rc normaliser must agree. The test "matches browser key events" (`ts:__tests__/vim.test.ts:130-145`) becomes a GPUI keystroke table test.

### 4.4 The pending-command state machine and the keymap

- `InputState` exactly as `core:1316-1353`: prefix and motion repeat digits, operator plus args, motion plus args, key buffer, register name, selected character, operator shortcut, change queue.
- The keymap is a data table, ported entry by entry from `core:75-262` (174 entries: 31 keyToKey, 60 motion, 20 operator, 8 operatorMotion, 47 action, 6 search, 1 ex, 1 idle; measured with grep). User entries (rc and `:map`) go in front. The noremap region is the last `DEFAULT_LEN` entries. Matching follows KY-05 and KY-06.
- **Seam problem, measured by reading:** `RcKeymap::resolve` (`rs:engine.rs:201-232`) is a pre-filter in front of the engine. It returns `Pending` for any prefix of an rc lhs. The engine does not work that way: among user and default entries, any full match wins over a partial one (`core:1599-1617`). With `nmap dx …`, a lone `d` is a full match of the `d` operator in the webview, so the `dx` mapping can never fire (`d` then `x` is "delete a character's span", not the mapping). `resolve(Normal, ["d"])` answers `Pending` instead (no test covers that; `rs:engine.rs:311-321` only checks `d w`). This changes behaviour, so the native engine must take rc entries into its own table, and `RcKeymap::resolve` must not be used as a pre-filter. `RcKeymap::apply` and the leader shadowing logic (`rs:engine.rs:158-197`) stay. They become the code that writes the user entries and stand-ins into the table, as `ts:engine.ts:336-381` does.
- Insert-mode mapping prefixes insert their characters tentatively and remove them on completion, at every caret (IN-05). The 200 ms timeout needs a timer from the host (`cx.spawn` with a delay). This is the one asynchronous edge of the model.

### 4.5 Plugging into the editor's key handling without changing anything while Vim is off

- The `Editor` (`ed:view.rs:318-392`) gets one field: `vim: Option<VimAttachment>` (the per-editor state plus a handle to the global). With `None`, every path below is a single `if let` that is skipped, and the existing editor tests are the proof that nothing changed.
- Order of a key press with Vim on, mirroring the webview:
  1. The window interceptor and keymap (`app-gpui/src/platform/input.rs:139-163`) run first, as the webview's capture-phase dispatcher does. They are made to honour the shortcut-conflict handlers: implement `DispatchEnv::claimed` for the window's `Env` (`app-gpui/src/platform/input.rs:226-238`) with `vim_claims` (`rs:conflicts.rs:85`). That is the native meaning of the webview's `KeyClaim`: return `Pass` so the key reaches the editor (`app-gpui/src/platform/dispatcher.rs:121, 309`). The other native mechanism, `claim_keys` (`app-gpui/src/platform/input.rs:77-88`), consumes the key and is the wrong counterpart.
  2. `Editor::key_down` (`ed:view.rs:1705`), first thing: a plain Escape outside Visual tries the editor's `EscapeHandler` first (A7, `ed:view.rs:1538-1544`). Then the key goes to the engine. `Handled` or `Pending` → `cx.stop_propagation()`. `Pass` → the existing code below runs unchanged. That covers Insert typing, Enter, Backspace, arrows, and ⌘Z/⌘C/⌘V (`ed:view.rs:1708-1727`).
  3. Printable keys. `key_down` returns early for unmodified letters (`ed:view.rs:1818`, `_ => return`), and the text arrives through `EntityInputHandler::replace_text_in_range` (`ed:view.rs:2083-2101`). In Normal, Visual and operator-pending modes, the engine must therefore take printable keys in step 2 and stop propagation. Hypothesis: stopping propagation in a key-down listener keeps GPUI from delivering the text to the input handler. This is gpui-kit behaviour, and its source is under the home directory, which this reading may not open. Settle with a window test before S1 lands: type `x` in a Normal-mode editor and assert the text is unchanged. As a second line of defence, `replace_text_in_range` with Vim not inserting hands the text to `VimEngine::text_input` instead of typing it. That also covers dead keys and ASCII IME commits (KY-08, A5).
- Paste in Normal (KY-09): `Editor::paste` (`ed:view.rs:1345`) calls the engine's paste rule first (move right one, enter Insert), then pastes as now.
- `<C-c>` with a selection on non-Mac (MD-06): the editor copies, then the engine gets `<Esc>`.

### 4.6 Undo grouping

Hypothesis: the webview's undo unit is one CodeMirror history event per Vim command, or more than one command when they come quickly. The adapter labels a command's first change `input.type.compose.start` and later ones `input.type.compose` (`cm6:80-104`). CodeMirror always joins `input.type.compose` into the previous event (`node_modules/@codemirror/commands/dist/index.js:499-513`, regex at `:488`). But the first change, `input.type.compose.start`, also matches the joinable pattern, so it joins the previous event when adjacent and within 500 ms (`:502-505`, `newGroupDelay` at `:212`). Quick adjacent commands (`xx`, `dd` twice) may therefore undo together. An insert session's typing is plain `input.type` and joins by the same adjacency rule. Hypothesis: so `u` after `cwfoo<Esc>` undoes the change and the typing together only when typed quickly, and in two steps otherwise. Settle at G3 with a vitest in the webview that dispatches with explicit `Transaction.time` values, covering `cw…<Esc>`, `xx` and `dd dd` both quickly and slowly.

Natively, `History::record` joins only edits of the same non-`Other` kind within `GROUP_DELAY_MS` = 500 (`ed:history.rs:12, 76-100`), and every selection change seals (`ed:history.rs:102-105`; `ed:view.rs:945`). The design adds `History::begin_group()` and `end_group()` (one group id for every record in between, no sealing), opened and closed by the host around each `handle_key` that edits. The insert session then follows the existing `Insert` joining rule, which has the same 500 ms window as CodeMirror's. Whether the Vim change and the following typing join must match the webview's measured rule.

### 4.7 Ex commands: where the IDE's commands attach

The engine's parser takes the range first (EX-01), then matches the name. The IDE's commands are entries in the engine's command map, as `defineEx` makes them (A8): `write/w`, `wall/wa`, `quit/q`, `qall/qa`, `wq`, `xit/x`, `action`. `handle_ex` (`rs:engine.rs:56-70`) cannot stay in front of the engine. It answers `Engine` for `'<,'>w` because it reads a name from the first alphabetic run, and `:2,5w` would never reach `write`. Its table (`rs:engine.rs:24-31`) and `run_ide_action` (`rs:engine.rs:46-53`) become the bodies of those map entries. `ExOutcome::Run` and `ExOutcome::Status` become host calls, deferred after the key as `ts:engine.ts:265-268` does. The rc's `mapEx` entries (A13) run through the same dispatcher.

### 4.8 Caret, selection, status item and command line

- Caret: the paint loop draws a 2 px bar per head when focused (`ed:view.rs:2735-2741`). With Vim attached it draws the shape the mode asks for (`cm6:1221-1296`):
  - a block over the character at the head (one non-breaking-space width at EOL or on a tab), in Normal, Visual and operator-pending modes;
  - in Visual, the block on `head-1` when the anchor is before the head (VI-03);
  - in Visual block, a block only at the primary range;
  - a block of 50 % height while keys are pending (`vim.status` non-empty);
  - 20 % height in Replace;
  - the usual bar in Insert.
    Colours follow the IDE theme override: the caret colour at 60 % when focused, a 1 px outline when unfocused (`ts:engine.ts:221-231`). Natively, the unfocused editor paints no caret at all today (`if focused`, `ed:view.rs:2735`); Vim needs the outline there.
- Selection: Visual ranges are ordinary editor selections (VI-02) and paint as today (`ed:view.rs:2640`).
- Search highlight: a new `MarkLayer::Vim` and a mark kind with the adapter's colours (`#ffff0054` light, `#00ffff8a` dark, `cm6:1318-1319`), set by the engine through the host (`Editor::set_marks`, `ed:view.rs:706`). The marks follow edits by themselves (`ed:marks.rs:95`). The adapter highlights by dispatching CodeMirror's `setSearchQuery` (`cm6:404-426`). The IDE's find model resets its excluded matches on that effect (`src/editor/core/cm/find.ts:77`), so a Vim search clears Find's exclusions. No IDE theme overrides `.cm-searchMatch` in the main editor; the only override is the diff editor's (`src/features/vcs/cm.ts:416`). Hypothesis: the find bar, when opened after a `/` search, starts from the Vim query; settle by trying it in the webview.
- Status item: `vim_item` exists (`app-gpui/src/workbench/status_items.rs:217`). It is fed from `mode_changed` through `VimModeState::changed` (`rs:mode.rs:34`). The same event sets the `vim.mode` context (`rs:mode.rs:175`) and emits `inputModeChanged` for plugins (`src/editor/api.ts:484`; `src/features/plugins/runtimeUi.tsx:338-339`), only while that editor is focused (`ts:engine.ts:203-208`).
- Command line: a bottom strip inside the editor's element, the counterpart of `.cm-vim-panel` (CL-01 to CL-08), holding a prefix label and a single-line `TextField` (the widget the find bar uses, `ed:find_bar.rs:467`). It is shown only while a prompt or message is open. The prompt's key-down hook implements history, `<C-u>` and Escape (`core:1795-1850, 1925-1955`). The key-up hook implements incremental search and the `:s` live highlight (`core:1956-1975`). Messages use the short and long rules of CL-03 and CL-04.

### 4.9 IME and the existing additions

`rs:ime.rs` is the IDE's Normal-mode composition rule (start, track, end, finish; transient changes). It attaches to `replace_and_mark_text_in_range` and `unmark_text` (`ed:view.rs:2103-2131, 2078-2081`) while Vim is attached and not inserting. Its `replay_key` goes to `VimEngine::text_input`. `is_transient` decides the edit's history and sync handling, which needs a "transient" flag on edits in the editor. The native editor has no transient-edit notion: `grep -rli transient app-gpui/src` lists no file under `app-gpui/src/editor/`, and `Editor::send` always records and syncs (`ed:view.rs:1121-1135`). I4 adds one (no undo entry, no backend sync). `rs:mode.rs` stays the app-level state machine: its `LoadEngine` and `InstallContribution` effects attach a `VimAttachment` to every editor and detach it. `rs:settings.rs` and `rs:conflicts.rs` feed `DispatchEnv::claimed`.

## 5. Slices

Each slice is sized for one writer: about 800 to 1,500 lines with tests. Engine slices work against `FakeHost` (4.2) and need no window. Test names follow the checklist IDs (for example `mo_08_w_treats_punctuation_runs_as_words`). Each slice also transcribes the `suite` cases listed under its items as table-driven tests: start text, keys, expected text and cursor. Those cases are the parity oracle.

By the inventory's rule, a row is at parity only when a Rust test shows it in the app, and model-only code counts as `[m]` (`docs/gpui-port/INVENTORY.md:3-5`). The engine slices S1–S14 therefore complete no inventory row by themselves. Rows flip only in the integration slices I1–I4.

Gates to run before the slices that depend on them. They are cheap static or one-test checks that de-risk the expensive work:

- G1, before I1: a window test proving that a stopped key-down suppresses text input (R2).
- G2, before S11: the owner's decision on the regex engine (R1).
- G3, before I1: a measured webview undo rule (R3), including whether quick adjacent commands merge.

## 6. Risks and unknowns

Ordered by size.

- **R1. The regular-expression dialect (the largest risk).** The default is `pcre` on, which means the user's pattern is a JavaScript `RegExp` source (SR-05, `core:5026, 5237-5279`). `nopcre` translation itself emits lookbehind and lookahead (`core:5107-5156`). The crate already in `app-gpui/Cargo.toml:58`, `regex`, has neither lookaround nor backreferences. Its `\w`, `\d` and `\b` are Unicode by default where JavaScript's are ASCII, and its case folding differs. `fancy-regex` exists in `app-gpui/Cargo.lock:2811`, but only as a dependency of `jsonschema` (measured with awk over the lock file), so using it directly is a new direct dependency, which D139 reserves for the owner's yes (`docs/gpui-port/DECISIONS.md:1270`). A JavaScript-compatible engine (Hypothesis: `regress` implements ECMAScript regex semantics) would also be new. Settle at G2: the owner picks (a) `fancy-regex` with an ASCII-class translation layer, (b) an ECMAScript engine crate, or (c) `regex` plus a recorded list of unsupported constructs. Then run the 34 `testSubstitute` and the `/_*` suite cases as the differential corpus.
- **R2. Key delivery.** Printable keys reach the editor as text input, not only as key-down (`ed:view.rs:1818, 2083-2101`). Hypothesis: `cx.stop_propagation()` in the key-down listener suppresses the text input. This is gpui-kit behaviour I could not read (its source is under the home directory). Settle with G1, a window test. Measured: GPUI's `Keystroke` has exactly the fields `key`, `modifiers` and `key_char` (it is destructured without `..` at `app-gpui/src/platform/input.rs:286`), so it carries no physical key code, and KY-03 (non-Latin layouts) cannot be ported from it. KY-03 stays a recorded gap unless gpui-kit exposes the physical key. Dead keys and AltGr reach the editor as text or IME (`app-gpui/src/platform/dispatcher.rs:260-272, 286-288`). The `text_input` path (4.5) covers them, but needs window tests per platform.
- **R3. Undo grouping and edit origins.** The webview's undo units come from CodeMirror's history joining rules applied to the adapter's `input.type.compose` labels, and they are time-dependent for insert sessions (4.6). Native history seals on every selection change and never joins `Other` edits (`ed:history.rs:76-105`). Without the group API, `u` after `dd` would be fine but `u` after `cw…<Esc>` or `.` would need several presses. Settle at G3: measure the webview rule with a vitest that sets `Transaction.time`, then encode it in I1's tests.
- **R4. The rc seam disagrees with the engine.** `RcKeymap::resolve` treats an rc prefix as pending, where the engine fires a full default match first (4.4; `rs:engine.rs:219-224` against `core:1599-1617`). This is settled by reading: the native engine must own the matching. Remaining unknown: whether anything outside `rs:engine.rs`'s tests already relies on `resolve`. A grep shows no caller outside `features_a/vim` (`grep -rn "RcKeymap" app-gpui/src`). Re-check before S1.
- **R5. Licence and attribution.** A faithful port is a derivative of the MIT-licensed engine and its suite (`node_modules/.pnpm/@replit+codemirror-vim-core@0.1.0/node_modules/@replit/codemirror-vim-core/LICENSE`). The repository's practice for MIT-derived material is a notice with the full licence text in `THIRD_PARTY_LICENSES.md` (for example `THIRD_PARTY_LICENSES.md:9, 47-53, 96`). The owner should confirm before S1 that the port gets the same entry.
- **R6. Viewport-dependent motions.** H/M/L use 6 px and 10 px tolerances (`core:5566-5575`). `<C-d>` scrolls by pixel deltas (`core:2480-2496`). `zb` measures the last character's box (`core:3002-3018`). `gj`/`gk`/`g0`/`g$` are display-line moves, and the webview has a Soft-Wrap toggle (`src/editor/core/gutterMenu.ts:45`). Hypothesis: the native editor does not soft-wrap (no wrapping code in `ed:view.rs`), so with soft wrap on these differ until a native soft wrap exists. Settle by checking the native Soft-Wrap action's implementation, and compare H/M/L on a partly visible top line in both builds.
- **R7. Asynchronous edges.** In the webview: `"+` paste is asynchronous (`core:3254`), highlights debounce 50 ms (`core:5418-5442`), the insert-mapping timeout is 200 ms (`core:964`), IDE Ex commands are deferred by `setTimeout(0)` (`ts:engine.ts:265-268`), and IME finishes on a timer (`ts:engine.ts:123`). Natively these are host timers. Tests need a controllable clock (as `History::record` already takes `now_ms`, `ed:history.rs:83`).
- **R8. Cross-editor global state.** The search query and direction, registers, macros and the jump list are global by construction (`core:762-784`). Measured: the jump list replays positions of other documents in the current editor (4.1; `cm6:992-1007`, `core:2952-2964`). A port that keeps per-document jump lists would differ, so the owner must choose between parity and a fix.
- **R9. Selection normalisation.** The native editor sorts and merges ranges (`ed:view.rs:954-958`). `commands::normalize` merges a range only when it overlaps the previous one, or when a caret starts at or before the previous end (`app-gpui/src/editor_commands/mod.rs:318-330`). Block rows lie on different lines, separated by a line break, so they never merge, even when they are empty. What remains: the main index after normalisation must be the head row (VI-02). S10 tests it.
- **R10. Folds.** Native `set_selections` opens every fold that any caret enters (`ed:view.rs:941-944`). CodeMirror 6 clears the folds touched by the main selection head on every selection change (`node_modules/@codemirror/language/dist/index.js:1342-1344`). Both builds therefore unfold when a Vim motion lands in a fold. The difference is secondary carets (Visual block, multiple cursors), which unfold natively but not in the webview. Low risk. I1 records it.
- **R11. Unmatched non-printable keys in Normal.** These fall through to the editor (MD-12). Hypothesis: in the webview, `<Tab>` in Normal therefore runs the editor's indent. Natively `Editor::tab` (`ed:view.rs:1468`) would do the same, but this needs a webview check per key (Tab, Enter in Insert, ⌘-shortcuts).
- **R12. Tags and tokens.** `it`/`at` need element nodes (TO-06), and `%`, quote objects and `[m` need token classes (MO-16, TO-03). Hypothesis: `literal_tree` (`ed:view.rs:895`) is empty until highlights arrive (its doc comment says so), so a Vim command issued right after opening a file could behave differently from the webview, which parses synchronously (`ensureSyntaxTree`, `cm6:707-720`). Settle with an I1 test on a freshly opened file.
