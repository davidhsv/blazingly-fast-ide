# Preliminary measurement: native GPUI app against the Tauri app (2026-11-17)

**This is a pilot, not a campaign: one run per app.** The owner read these numbers and decided on them that the rewrite pays off, that the three-repetition campaign is not needed, and that the parity work resumes (DECISIONS D162, D163, D165 to D168). The final measurement at parity, with repetitions, still stands and goes to `REPORT.md`.

## Verdict, as far as one run can carry it

- **Memory: the native app used about half to a third of the Tauri app's memory.** With ten Java files open it held 258 MiB against 749 MiB; after ten minutes idle 372 MiB against 787 MiB. The gap is the WebKit helper processes (504 to 606 MiB once editors are open); the two apps' own processes are of similar size, and the native one is the larger (372 against 270 MiB at idle).
- **CPU: the native app used a fraction of the Tauri app's CPU wherever an editor was on screen.** Opening and scrolling ten files cost 6.2 s against 42.8 s; idle with an editor focused cost 0.2% of one core against about 7% while the Tauri app was in front.
- **Part of both gaps will close as native features land.** The native editor today runs none of about fifteen per-file code-insight features that the Tauri editor runs (list below). The differences are two to seven times on one run each, which repetitions would not reverse; how much remains at parity is not known and is what the final measurement answers.
- **What does not depend on missing features:** the cost of the web runtime itself. At cold start, before any project, with both apps showing a welcome window, the Tauri app holds 174 MiB against 117 MiB and its helpers account for 132 MiB of that.

## What was measured, and how

- **Builds:** both release binaries from one export of commit `18b54813b`, built offline (`pnpm tauri build --no-bundle` with the identifier `ai.l0ng.openidea.measure`; `cargo build --release --locked --bin openidea-gpui`), link-time optimisation as each ships (Tauri thin, native fat). rustc 1.99.1.
- **Machine:** Apple M1 Pro, 10 cores, 32 GiB, macOS 14.7.1. The owner's own work ran beside the pilot (a java process, Docker's virtual machine, a browser): load average 3 to 6. Memory does not depend on it; CPU seconds depend on it a little; durations are set by the driver's waits and are not a speed result.
- **Project:** an APFS clone of the owner's large Java monorepo, detached from the original (D165). Both apps index **15,822 files** in about 2 s; the tree's other 1.2 million files are ignored paths.
- **Driving:** key events posted to the measured app's own PID, the same keys for both; waits on the window title, the backend's log lines, the settings file and the process set's CPU. Deep mode without language servers (none is installed for either app). No network: no connection to an outside host was seen in any run.
- **Metric:** per second, `proc_pid_rusage` of the app, its children and (Tauri) the WebKit helpers it is responsible for: physical footprint (the number Activity Monitor shows), CPU time, wakeups. The sampler's sum matched `footprint -p` (787 MB at the Tauri idle). Steady is the median of the last 10 samples of a scenario (60 for idle). A scenario's CPU is the increase of the set's cumulative CPU between its boundary samples.
- **Windows:** native 1536×1079 points, Tauri 1440×900, both on the built-in display in the pilot. The native window is the larger, which counts against the native app if at all.
- **Isolation:** the Tauri build ran as its own process with its own single-instance socket, data folders and WebKit storage under the run's folders; the owner's installed app was not running at any check and nothing outside the run's folders and the fake home was written (reports under `notes/reports/measure_run1.md` to `measure_run3.md`).

Peaks: the Tauri set peaked at 995 MiB while the files opened and at 987 MiB during idle; the native app's peak was 372 MiB, at idle.

- **The Tauri idle figure mixes two states.** For about the first half of its idle window the Tauri app was in front and used about 7% of a core with 320 wakeups a second; then another window took the front and it fell to 0.2% and 93 wakeups (WebKit throttles a background view). The native app stayed in front the whole time at 0.2%. So 4.3% understates the Tauri app's idle cost in front and overstates it in the background.
- **A second observation** (the evidence run of stage 3: one run per app, idle 60 s, a compiler running beside it with a load up to 19, and the two windows on different displays, so it is weaker than the pilot): with ten files open 285 MiB against 712 MiB, CPU for opening them 7.1 s against 40.7 s, idle 0.1% of a core against 4.0% with both in front for all 60 seconds. It agrees with the pilot.

## What this does not show

- Spread: there is one run per app. No median, no range.
- Memory and CPU with language servers running (Deep mode with jdtls): none is installed, for either app.
- The native app at parity. 1,171 of 3,782 inventory rows are at parity; the editor features listed for S3 are the ones most likely to add memory and CPU.
- Whether the native app's own process keeps growing: it went from 258 MiB with ten files open to 372 MiB at idle across Find, the Git log and two mode switches with nothing closed. Whether that is retained state that should be released is to check.

## Defects and gaps the measurement found in the native app

- The Git log on this project drew no graph and no commit subjects, and appears to list every ref where the webview lists `HEAD` by default.
- The welcome window shows version 0.1.40 where the Tauri app built from the same commit shows 0.1.46, and offers only "Open".
- On first opening a fresh clone the project's `.git/index` was rewritten 0.7 s after the native app opened it, although optional locks were switched off; whether the Tauri app does the same was not established (the index was already fresh when it ran).
- These are in `notes/OWED.md`.

## For the final measurement

- Both windows on the same display and at the same size, checked before each run (the Tauri window opened on the external display in the last runs).
- The Git log showing the same refs in both apps; the scenario without scrolling, or with one that is proven to do the same work.
- The frontmost application is now recorded every second and an idle window that loses the front is marked; nobody at the machine for the two hours.
- Three repetitions per app, alternating, on an idle machine.
- Scripts as last run: `measure/scripts_run/` (their changes against the design's originals in `CHANGES_stage1.diff` to `CHANGES_stage3.diff` and the stage reports; the full tables are in `measure/pilot/`). Command: `run_all.sh <base> --reps 3 --capture --runs-root <base>/campaign`. Captures of the apps' windows show the project's source and are never committed.
